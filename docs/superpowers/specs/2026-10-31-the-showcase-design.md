# The Showcase -- a shared link, the engine's own evidence, liquidity and overlays

*2026-10-31. The owner passed on an outside roadmap (Gemini's) and asked for the
improvements it was right about, not for the roadmap. The owner chose "use your
set" after the audit below, and the plan is this document's last section.*

## Why

Someone following a link to the public site finds a good workstation, and three
things stand between them and it:

1. **A link previews as nothing.** `curl /` returns fifteen characters of text
   and no Open Graph or Twitter tags. `/robots.txt` and `/sitemap.xml` return
   the app's HTML, and any unknown path answers 200.
2. **The claim the project is built on is not visible.** The public `/engine`
   page draws an explanatory diagram marked "not live", quotes a benchmark by
   hand from `docs/overview.md`, and its live panel is off.
3. **Two pieces of real analysis stop short.** Liquidity-adjusted VaR is a tested
   kernel (`lib/liquidity.ml`) that nothing yet runs, and a 13F import drops every
   option row, which is most of the risk in some of the funds it lists.

## The audit

| The roadmap asked for | What is there | Decision |
|---|---|---|
| Crawler text and metadata | Nothing | Do it, plus robots, sitemap, real 404s and per-route metadata |
| An interactive Incremental graph | The real one is `web/graph.js`, behind the password; the public one is a drawing | Replay a recording of the real engine |
| A benchmark panel | `make bench`, `Scaling_probe`, `/api/ops` percentiles and `/api/ops/kernels` exist | Generate the numbers and serve them; no new suite |
| GPD/POT VaR and ES | `evt_pot`, tested against scipy | Nothing |
| L-VaR | `lib/liquidity.ml`, a kernel the engine does not call | Port it to Quant, with the same formula and its worked example as a parity test |
| 13F multi-class and option parsing | Parsed and aggregated, then options are dropped | Carry options into the portfolio as an overlay |
| Berkshire, Bridgewater, UVIMCO presets | The first two are listed; EDGAR full-text search finds no 13F-HR under UVIMCO's name | One-click filers; no UVIMCO |
| `/api/v1/...` | `/api/docs` and `/api/openapi.json` are public | Nothing; a renamed path adds nothing |

Three of the roadmap's ideas are wrong for this project, and are not to be
revisited without new information:

- **"All 8 VaR/ES models through Incremental."** The models are Python. Incremental
  runs in the OCaml engine, with a different and smaller set of risk numbers.
- **An in-browser stress test.** It would time JavaScript and call it the engine.
- **Wasm.** `lib/` is one library with Async and Owl in it, and Owl needs native
  numerics. It is a library split and an Owl replacement, for a demo a recording
  can make honestly.

## Goals

- `curl` of any public page returns that page's title, description, canonical
  URL, preview tags and a short, true description of the page.
- `/robots.txt` and `/sitemap.xml` are what they say they are, and an unknown
  path is a 404 that still renders the app's own not-found page.
- `/engine` shows what really recomputes for each kind of input, measured from
  the real engine, and benchmark figures generated by a command rather than typed.
- `/engine` shows the live engine's latency and throughput with no book data.
- `/risk` shows L-VaR, liquidation time and impact for the active portfolio.
- A 13F import can carry the filing's options as a stated delta overlay.

## Non-goals and anti-goals

- No position name, size or limit threshold of the live book on the public site.
  This is the owner's standing rule; the bridge as written would break it.
- No synthetic market. The recording runs real closes and says it is a recording.
- No number typed into copy. Fallback text describes; figures come from artifacts.
- No marketing voice: the fallback is plain sentences in the site's own terms.
- No new infrastructure, no CSP widening, no `--live` deploy, no edit to the
  droplet's book.
- `docs/engine.md` is left alone: the owner has uncommitted work in it.

## Decisions

**Findability.** One Python table of public routes (`api/seo.py`) gives each path
its title, description and fallback paragraph, and a test holds it equal to
`quant/web/src/lib/routes.ts`. FastAPI fills marked regions of the built
`index.html` per request, because it already answers every path. `robots.txt` is a
static file; `sitemap.xml` is rendered from the table. Unknown paths keep the app
shell with status 404. The fallback sits inside `#root`, so React replaces it, and
the stylesheet holds it hidden for its first moment so a reader with JavaScript
never sees it flash; no inline script changes, so the CSP hash stands. The preview
image is a real capture of The Machine.

**Recording, not simulating.** A new `make propagation` runs a program beside the
benchmark, which drives the real `Graph` with `Recompute_log`, on a nine-ETF
example book whose closes and returns come from the committed fixtures. For each
input kind (a price tick, a fill, a day's returns roll, the factor series, the
cash balance) it records what ran, what changed and what a cutoff held, and the
median stabilize. It writes `docs/perf/propagation.json`, which follows the
`kernels.json` pattern: committed, copied into the image, served at
`GET /api/engine/propagation`, 503 when absent. The page draws Incremental's own
topology from that file. The machine that produced it is stated beside every
timing. The incremental-versus-full figures come from the same run, with the
benchmark's existing full-recompute baseline.

**The bridge reads aggregates by default.** A new `GET /api/engine/vitals` copies
named numeric fields out of `/api/ops` and the counters out of the snapshot. It
never forwards a body. `status`, `snapshot` and `history` carry the book, so they
are refused unless `OHCAMEL_QUANT_ENGINE_BOOK_PUBLIC` is set, which production
leaves unset and the local demo harness sets. Status without it keeps counts and
loses symbol names. Only after this ships is `OHCAMEL_QUANT_ENGINE_URL` set on the
public host.

**L-VaR mirrors the engine.** The same three figures as `lib/liquidity.ml`: days to
liquidate at a participation rate of ADV, Toth et al. (2011) square-root impact,
and Bangia et al. (1999) L-VaR as VaR plus the cost of crossing the half-spread,
with the spread-volatility term at zero as the engine has it. The defaults are the
engine's. There is no quote history to measure a spread from, and the daily
high-low estimators were tried on the nine fixture ETFs and rejected: over the
last year Corwin-Schultz (2012) and Abdi-Ranaldo (2017) put SPY at 18 and 15 bps
against a half-spread near 1 bp, because on names this liquid the day's range is
volatility, not spread. So the half-spread is a stated, editable assumption (the
engine's own: 5 bps by default, SPY 1.0, TLT 1.5), and the page says so.

**The overlay states its assumption.** A 13F reports an option's underlying
notional, with no strike or expiry, so it cannot be priced. The overlay is a
delta-one exposure at an assumed |delta| (default 0.5, adjustable): calls long,
puts short, on the same equity base as the stock weights, netted by name. It is
off by default, and turning it on says that it is an assumption. The equity book
keeps its 100% rescale, and the overlay does not rescale with it.

## Plan

1. **Findability**: `api/seo.py`, `app.py`, `index.html` markers, `robots.txt`,
   preview image, smoke checks.
2. **Recording**: split the benchmark's baseline into a shared module, add
   `bench/propagation.ml`, `make propagation`, the artifact, its route.
3. **Engine page**: the replay figure, generated benchmark tiles, vitals panel.
4. **Bridge**: `vitals`, the book gate, status redaction, compose and env docs.
5. **L-VaR**: `risk/liquidity.py`, `POST /api/risk/liquidity`, a `/risk` section,
   methodology entries. Compare spread estimators on the fixtures first.
6. **Overlay**: filing payload, builder toggle, one-click filers, methodology.
7. **Documents and verification**: status, READMEs, counts, full suites, browser.
